A column read through its key splits the key once instead of on every cell, so default cell reads take about half the time. A tree read from a parent-id column indexes its rows once, so 8,040 rows with parents listed last build in 2 ms instead of 181 ms. A table with no cell spans gives every row one shared cell list instead of building one per row. A row patch made by the CommonJS build updates a view held by the ESM build incrementally, and the other way round, instead of re-filtering every row. Folding, unfolding or paging groups keeps the groups and their totals and reads no rows: collapsing one of 100 groups over 50,000 rows takes 1.9 ms instead of 8.4 ms, and a group header and its footer share one list of row ids. A table with no filters feature and no `filterFn` skips the filter pass instead of calling a predicate that keeps every row. A column with `i18n` resolves its locale once per sort and once per column for `cellValue`, not once per row: sorting 50,000 rows by such a column takes 44 ms instead of 56 for `ar` and instead of 70 for `ar-EG`. A nested filter tree is prepared once per pass, its definitions, predicates and values resolved before the rows are read and each group stopping at its first decisive branch: a five-condition tree over 50,000 rows evaluates in 4.7 ms instead of 73. Repeated `rowByKey` reads of the same rows use an index built on the second read: 200 lookups near the end of 50,000 rows take 4.9 ms instead of 86, with a single read unchanged. Pinned scrolling indexes the page rows once per row array: 16 window updates over 50,000 rows take 3.4 ms instead of 49. `pivot` reads each row's dimensions once and indexes the rows by row and column path: 20,000 rows with 400 groups pivot in 19 ms instead of 552, and with 10 groups in 21 ms instead of 45. A frontend table whose search is its only filter takes the searched rows from the search it already ran: a warm keystroke over 50,000 rows reads each row id once instead of twice, 6.9 ms instead of 11. New rows that arrive with a changed query or new filter semantics are evaluated once under the new view, not under the old view and again: a data and sort change over 50,000 rows calls the filter 50,000 times instead of 100,000. Extra rows find the cells a row span carries across them in one walk for the whole body: 202 extra rows over 3,000 rows by 20 columns take 2.7 ms instead of 97.
